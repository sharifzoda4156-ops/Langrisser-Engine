# Langrisser Engine

Открытый исследовательский проект движка для **Langrisser Mobile / Apex Arena**.
Цель — агент, который играет заданными героями, исследует бан-пик, обучается
через самоигру и проходит проверку против сильных игроков.

Headless simulation, external-player test stand, reproducible matches, and a
roadmap toward learned draft and battle policies.

Основная цель — **глобальный сервер**. Китайскую версию используем как источник
ранних данных для будущего анализа новых героев, сочетаний и бан-пика. В плане
предусмотрены отдельные режимы Global, China и прогноза Global с выбранными
будущими добавлениями. Срок выхода на глобале подтверждаем по каждому обновлению;
фиксированная задержка в шесть месяцев не предполагается. Сборка региональных
снимков и Preview уже реализована для данных и тестовых матчей; реальные бои
Global/China пока не поддерживаются. См. [план версий и прогнозов](docs/REGIONAL_RULESETS.md).

## Текущий статус: фундамент и рабочий стенд

**Это ещё не точный симулятор Langrisser и не обученная нейросеть.**
Первая версия реализует `protocol-fixture-v0`: маленькую синтетическую игру
для проверки полного цикла «бан-пик → бой → результат → запись партии».
Все её персонажи имеют префикс `fixture_`. Формула тестового урона, драфт и
правила ходов намеренно искусственные. Применять их к реальному Apex нельзя.

Уже работает:

- Нативное ядро C++20: движение по взвешенной сетке, препятствия, допустимые
  действия, тестовый бой, чередование действий и конечный результат.
- Python-стенд без сторонних runtime-зависимостей: CLI и локальный JSON HTTP API.
- Подключение внешнего игрока: агент получает наблюдение и список разрешённых
  действий, затем отправляет выбранное действие.
- SQLite: сохранение матчей, атомарное применение решений, защита от устаревших
  ответов и повторного выполнения одного запроса.
- Реплей: восстановление партии по исходному сценарию и действиям с проверкой
  событий и SHA-256 хешей состояний.
- Автоматические партии между `random` и `heuristic`, экспорт реплеев и
  траекторий с конечным результатом для каждого игрока.
- Тесты ядра, драфта, перезапуска, конкурентных ответов, реплеев и HTTP API.
- Замороженные региональные снимки: точные версии, доступность по датам,
  проверка зависимостей и Preview с явным списком будущих добавлений.
- Привязка снимка к матчу: состав, характеристики, карта и драфт сверяются до
  создания матча; происхождение снимка сохраняется в реплее и отчёте.
- Отдельный режим `action-lifecycle-lab-v1`: повторное действие, восстановление
  действия союзника, отход после атаки и раздельные таймеры. Подтверждённые
  описания механик отделены от допущений лабораторного режима.

Пока отсутствуют: реальные герои/солдаты и их точные механики, Guard, способности,
предметы, случайные срабатывания, точные правила Apex, нейросеть, MCTS, обучение,
лига соперников и графический интерфейс. Команда `selfplay` **собирает партии
простых ботов, но не обновляет веса модели**.

## Быстрый запуск

Нужны Python 3.11+ и компилятор C++20 (`g++` или совместимый `CXX`).
Поддерживаемое окружение первой версии — Linux. Docker, GPU и API-ключи не нужны.

```bash
python scripts/build_native.py
python -m unittest discover -s tests -v
python -m apex_engine selfplay --episodes 2 --seed 1 --output runs/demo-001
python -m apex_engine verify runs/demo-001/episode-00000.json
python scripts/smoke_external.py --output runs/external-001
```

`--output` должен указывать на новую папку: старые результаты не перезаписываются.
В ней появятся `summary.json`, реплеи `episode-*.json` и `trajectories.jsonl`.
Траектории содержат наблюдения, доступные действия, сделанный выбор и
`terminal_value` (`+1` победа, `0` ничья, `-1` поражение).

## Региональные снимки и Preview

Полная проверка нового пути через CLI и отдельных внешних игроков:

```bash
python scripts/smoke_regional.py --output runs/regional-demo-001
```

Она создаёт тестовые Global/CN-снимки, добавляет один явно выбранный будущий
отряд в Preview, проводит партии и проверяет реплеи. **Все персонажи этого
примера искусственные**, даты 2000 года служат только для проверки доступности.
Команды `content build`, `content preview`, `content verify` позволяют работать
со снимками отдельно. `create --snapshot FILE` и `selfplay --snapshot FILE`
связывают сценарий с точными данными снимка.

Есть также отдельный небольшой каталог подтверждённых дат релиза D-Boy и
Shinya Aiba. Он помечен `release_metadata` и не содержит боевых параметров;
использовать его вместо реализованных игровых механик движок не разрешает.
Проверка хеша подтверждает целостность снимка, а не правильность игровой формулы.
Подробности и ручные команды: [снимки контента](docs/CONTENT_SNAPSHOTS.md).

## Порядок действий и длительности эффектов

```bash
python -m apex_engine selfplay --scenario scenarios/action_lifecycle_lab.json \
  --episodes 2 --seed 1 --output runs/lifecycle-001
python scripts/smoke_external.py --scenario scenarios/action_lifecycle_lab.json \
  --output runs/lifecycle-external-001
```

Новый набор правил помечен `mechanics_lab`. В нём раунд, активация отряда,
полное действие и дополнительное перемещение — разные события. Во время
повторного действия управление остаётся у того же отряда. Отход после атаки
разрешает только перемещение и не создаёт второго полного действия.

Это лаборатория проверки порядка событий: числа урона искусственные, эффекты
служат таймерами без изменения боевых характеристик. Начало отсчёта длительности,
кулдауны и другие допущения описаны явно и ещё требуют сверки в актуальном Global.
Реальные герои, Guard и их полные способности не заявляются реализованными.
Старый набор правил и его реплеи сохранены. Подробности:
[контракт и источники](docs/ACTION_LIFECYCLE.md).

## Стенд для Codex, Claude и других внешних игроков

```bash
python -m apex_engine --db runs/stand.sqlite3 serve --port 8765
```

Стенд слушает **только `127.0.0.1`**. Это локальное средство разработки без
аутентификации; не публикуйте порт и не ставьте публичный reverse proxy.
Запросы с браузерным `Origin` или посторонним `Host` отклоняются.
В этой версии все сведения тестовой игры открыты обеим сторонам.

В другом терминале:

```bash
curl http://127.0.0.1:8765/health
curl -H 'Content-Type: application/json' --data-binary @scenarios/protocol_fixture.json \
  http://127.0.0.1:8765/matches
```

Ответ содержит `match_id`. Игрок запрашивает своё решение:

```text
GET /matches/MATCH_ID/request?player=0
```

На своей очереди он получает `request_id`, `state_hash`, наблюдение и
`legal_actions`. Ответ отправляется в `POST /matches/MATCH_ID/actions`:

```json
{
  "request_id": "<из запроса>",
  "state_hash": "<из запроса>",
  "expected_version": 0,
  "player": 0,
  "action_id": "<из legal_actions>"
}
```

Все три идентификатора — полные lowercase SHA-256. `expected_version` берётся
из текущего ответа стенда. Идентичный повтор возвращает исходную квитанцию;
изменённый повтор или устаревшая версия отклоняется с HTTP 409.

Тот же протокол доступен через CLI, поэтому агент может работать обычными
инструментами терминала без отдельного HTTP-клиента:

```bash
python -m apex_engine create
python -m apex_engine request MATCH_ID --player 0
python -m apex_engine submit MATCH_ID --response response.json
python -m apex_engine replay MATCH_ID > runs/replay.json
python -m apex_engine verify runs/replay.json
```

Для примера внешнего адаптера смотрите [examples/external_player.py](examples/external_player.py).
Запустите два процесса, указав один `match_id` и разные стороны:

```bash
python examples/external_player.py --match-id MATCH_ID --player 0 --agent heuristic
python examples/external_player.py --match-id MATCH_ID --player 1 --agent random
```

LLM может заменить выбор baseline-бота своим решением. Внешняя LLM и обучаемая
политика — разные исполнители: участие LLM само по себе не меняет её веса.
Для непрерывной работы нужны отдельный процесс и подключённый исполнитель.

## Архитектура и дальнейшая работа

| Часть | Ответственность |
| --- | --- |
| `native/` | Нативные переходы состояния и генерация действий; сейчас только fixture |
| `apex_engine/game.py` | Версия правил, проверка сценариев, тестовый драфт, граница C++ |
| `apex_engine/content.py` | Каталоги, региональная доступность, снимки и явные Preview |
| `apex_engine/lifecycle.py` | Отдельные действия, повторные действия, отход и таймеры |
| `apex_engine/stand.py` | Долговечные запросы решений, транзакции и проверка реплеев |
| `apex_engine/agents.py` | Простые контрольные игроки и сбор траекторий |
| `scenarios/` | Явно версионированные входные данные |
| `data/content/` | Синтетические примеры и отдельные факты о релизах |
| `tests/` | Проверки поведения и протокола |
| `docs/` | Архитектура, план и требования к доказательствам механик |

Разработка движется к связке **точные правила → поиск и нейросеть → самоигра
в лиге → обучаемый бан-пик → независимая проверка силы**.
Сверхчеловеческая сила — цель исследования, а не текущий результат или обещание.

## Инструкции для агентов

Основной файл — [AGENTS.md](AGENTS.md). Для Claude есть точка входа `CLAUDE.md`,
для GitHub Copilot — `.github/copilot-instructions.md`.

**В публичном GitHub нет файлов, видимых исключительно ИИ-агентам.** Эти документы
открыты всем. Личные дополнения можно держать в игнорируемом `AGENTS.local.md`
на конкретной машине; они не передаются при клонировании. Ключи и другие секреты
не должны попадать в коммиты или инструкции.
